1. SQL 流水线：一条查询的加工顺序

前面零零散散学了 WHERE、GROUP BY、ORDER BY，现在把它们串成一条流水线。数据库执行一条查询的固定顺序是：

① FROM从哪张表拿数据（原料）
↓
② WHERE逐行筛选，不满足的扔掉第 1 课
↓
③ GROUP BY归堆第 1 课
↓
④ SELECT决定输出哪些列 / 算什么聚合
↓
⑤ ORDER BY对结果排序（DESC 从大到小）
↓
⑥ LIMIT n只要前 n 行
FROM → WHERE → GROUP BY → SELECT → ORDER BY → LIMIT，永远这个顺序

有个容易懵的点：SELECT 写在查询的最前面，但执行却排在第 4 步——就像点菜单先印在桌上（你先写 SELECT），菜却是后厨按流程做出来的（数据库按 FROM/WHERE 顺序加工）。所以 ORDER BY 里能引用 SELECT 里定义的别名（比如上一课的 ORDER BY 数量 DESC）。

2. 最近邻问题：错写法 vs 对写法

真实需求来了："离市政府最近的 5 家火锅店在哪？"

直觉写法（能对，但很笨）

先算每家店到市政府的距离，再排序取前 5。问题在于：为了找 5 家店，数据库要给全部 25 万行每行算一次距离、再整体排序——城市另一头的店也陪跑了。

试一试 2-2 · 笨办法（看看就行）
火锅店只有几千家所以还能跑。若是"全部 POI 里最近的 5 家"，25 万行都得算距离

专业写法：KNN 算子 <->

PostGIS 提供了专门的最近邻算子 <->（读作 KNN 距离）。把 ORDER BY 距离 换成 ORDER BY geom <-> 圆心：

结果和笨办法一样，但写法完全不同 —— 这一行就是 POI 系统里"最近设施检索"按钮的全部秘密
现成的坑（写这课时真踩到）：<-> 右边的点必须带 SRID——直接写 ST_MakePoint(114.3,30.5) 得到的点 SRID=0，和表的 4326 对不上，报错 mixed SRID geometries。标准写法是 ST_SetSRID(ST_MakePoint(...), 4326)（上面就是）。做练习 1 时别忘了这一点。

两种写法结果一模一样，那 <-> 好在哪？——它自己不"算距离"，只提供一个可排序的相对远近，配合下一节的索引，数据库不用碰 25 万行就能直接"顺藤摸瓜"拿到最近的 5 个。

3. 索引：为什么能快 100 倍

索引（index）就是数据的目录。新华字典 1800 页，查"周"字你不会从第一页翻到最后一页——你先翻目录（部首检字表），直接跳到 1600 页附近。数据库没索引时查东西只能"全表扫描"（从第一行摸到最后一行）；有索引就能按目录直达。

我们的库建表时就建好了两类索引：

索引建在服务什么查询
GiST（空间索引）pois.geom范围框选、ST_DWithin、KNN <->——所有空间判断
BTREE（普通索引）category 等列WHERE category = '餐饮' 这类等值/排序

GiST（通用搜索树）是空间数据专用的索引结构：把地图切块分层，先粗判"这个框内可能有目标吗"，再精查。实测（我们第 8 课会亲手做基准）：

查询有索引无索引加速比
KNN 最近邻1.3 ms132.9 ms100×
六边形密度聚合445 ms29 秒65×
最常见的索引事故：geom::geography 让"列变了形"。索引目录是按 geom 原样编的，查询里把列转成 geography 后，数据库认不出"变形后的列"对应哪本目录——所以我们的库里额外建了一本 (geom::geography) 的专用目录（表达式索引）。第 8 课细讲，现在知道有这回事就行。

再对比一个"天生没法走索引"的查询——不带任何条件的全表计数：

试一试 2-5 · 全表扫描长什么样
找 "Seq Scan on pois" —— 25 万行一行不落全部摸一遍，没有任何目录可翻
为什么全表计数不走索引？因为要数的是"全部"，每行都得摸到，翻目录反而多此一举——优化器自己会权衡。索引不是万能的，它服务的是"按条件缩小范围"的查询。

Seq Scan（顺序扫描）vs Index Scan（索引扫描）——以后调优就盯这两个词：分析查询慢，先 EXPLAIN，看到 Seq Scan 且表很大，八成是索引没被用上。

最热格子 3 万多个点（CBD 核心）—— 这张表就是前端六边形密度图的数据源

拆开看：FROM 里不再是"一张现成的表"，而是函数 ST_HexagonGrid 现场生成的一堆六边形（第 5 课的启发——函数返回几何，还能返回一堆几何）；LEFT JOIN ... ON 把每个 POI 分配到装它的格子里（第 0 课见过的 JOIN 今天不展开，第 3 课细讲）；再 GROUP BY 归堆计数。地图上那种蓝→红的六边形密度图，底层就是这张表配上颜色。

7. 练习 + 打卡

练习 1

找出离市政府最近的 3 家"医疗"类 POI，输出店名、子类、距离（米）。提示：套用试一试 2-3 的写法，把 subcategory 条件换成 category = '医疗'。

查看答案
SELECT name, subcategory,
       round(ST_Distance(geom::geography,
             ST_MakePoint(114.305,30.593)::geography)::numeric,0) AS 距离_米
FROM poi.pois
WHERE category = '医疗'
ORDER BY geom <-> ST_SetSRID(ST_MakePoint(114.305,30.593), 4326)
LIMIT 3;
每次运行结果可能略有不同（模拟数据里有同名店），距离大约在几十米级别——市中心医疗机构密度很高。

练习 2

把试一试 2-8 的格网大小 0.02 改成 0.05（格子变大 6 倍），最热格子的 POI 数变成多少？思考：格子越大，"密度图"是变粗糙还是变精细？

查看答案
最热格子约 5.5 万个点（几个 CBD 被并进了一个大格）。格子越大图越粗糙、格子越小越精细——但格子太小每格点数太少、图会变得琐碎。前端六边形图按地图缩放级别动态调格子大小（z11 用 0.03°，z14 用 0.006°），就是这个权衡。
